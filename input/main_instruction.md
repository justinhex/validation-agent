# Main Instruction — power-window-demo

This pack is the demo input for validation-agent: a simulated power-window controller (DUT) with its requirements.

## What's in this pack

- `requirements/` — the requirements to test (PW-001..PW-008, power-window behaviour).
- `dut/` — the device under test: a C++ simulated window controller (ECU, DoorControlModule, motor, sensors, switch, door handle, CAN bus).
- `context/` — the user's environment background (CI design, environment, version control).
- `instruction/` — project-specific steps (flash, failure handling, company tools, JIRA).
- `pack.yaml` — the pack manifest (name, version, path overrides).
- `mcp.json` — MCP server connection config (only when the project uses company tools).

## Rules the output must follow

1. **Output is 100% generated.** Everything in `output/` is generated by the agent. Never hand-edit it. If the output is wrong, fix the input or the agent and regenerate.
2. **Tests come from requirements.** Every test scenario maps to one requirement ID, tagged with that ID (e.g. `@PW-003`). No test without a requirement.
3. **Use only the bench API.** Generated test automation drives the DUT through the bench API only — no direct calls into the DUT internals.
4. **Generated files are marked.** Every generated file carries the header `# Generated by validation-agent — do not edit`.
5. **Same tests, both backends.** The test cases run on the simulated DUT (SIL) now and on real hardware (HIL) later — only the bench backend swaps.
6. **Failures follow the failure procedure.** When a test fails, follow `instruction/failure-handling.md`. Send nothing externally.

## Detailed instructions

- Flash the build onto real hardware (HIL): read `instruction/flash.md`.
- When a test fails: read `instruction/failure-handling.md`.
- Using the company's tools: read `instruction/tools.md` (connection config in `mcp.json`).
- Raising a JIRA ticket: read `instruction/jira.md`.
- The user's CI, environment, and version control: read `context/`.
